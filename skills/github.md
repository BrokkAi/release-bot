# GitHub release operations (built-in skill)

Use the installed `gh` CLI for GitHub. Use the configured host/repository explicitly on every command. The examples below use REPO for `[HOST/]OWNER/REPO`, SHA for the exact release commit, TAG for the release tag, and RUN_ID for a selected workflow run. Substitute actual values and quote shell arguments. Run `gh help` or the relevant subcommand's `--help` if a flag is unavailable.

During publication, use job.plan for the destination and required workflow list and use job.validated_at for the daemon gate. Discovery and code repairs below apply to preparation; publication only inspects the documented procedure and relevant new or failing runs.

1. Check authentication with `gh auth status --hostname HOST`. Read `.github/workflows/` and identify branch/tag/event filters, reusable workflows, permissions, environments, release assets and package destinations. Determine which workflows must run for this release. Do not disable checks or bypass required approvals.
2. Inspect Actions with `gh run list --repo REPO --commit SHA --limit 100 --json databaseId,workflowName,headSha,headBranch,event,status,conclusion,url`. A run from another SHA proves nothing about this release. Preserve separate branch, tag and event contexts. For larger histories use paginated `gh api` requests; an empty list or a missing required workflow is not success.
3. Inspect the specific run using `gh run view RUN_ID --repo REPO --json jobs,status,conclusion,headSha,url`. Retrieve failures with `gh run view RUN_ID --repo REPO --log-failed`; use `--job JOB_ID --log` or the jobs API when needed. Read the actual compiler, test, packaging or upload error before changing code.
4. Commit and push a focused fix when needed. Re-list runs for the resulting SHA. For a transient failure on unchanged code, use `gh run rerun RUN_ID --repo REPO --failed` when appropriate. Rerunning an old SHA does not test new fixes. Trigger `gh workflow run WORKFLOW --repo REPO --ref REF` only when the documented release process uses workflow_dispatch and supply its required inputs.
5. Wait by polling `gh run view RUN_ID --repo REPO --json status,conclusion` or `gh api` at 15–30 second intervals. Use a single bounded shell loop that prints only status changes and a heartbeat at most once a minute, stops on completion, and exits nonzero for failure or timeout. Do not use the default `gh run watch` output: it reprints the full job table every three seconds. Fetch detailed jobs/logs once when a run fails. Avoid repeated model turns just to poll unchanged status. Inspect the latest attempt; require conclusion `success`. Queued, waiting, in_progress, cancelled, skipped and missing runs do not count as a passed release. Do not let a successful branch run hide a failing tag-triggered run.
6. If branch protections require a PR, use `gh pr create`, inspect `gh pr checks --watch`, and merge only through permitted repository rules. Track the actual merged commit and its release checks.
7. Inspect the exact publication with `gh release view TAG --repo REPO --json tagName,isDraft,publishedAt,assets,url`. Confirm it is published, not a draft, and has every required asset. Download and validate artifacts when the project's release procedure requires it. Check package registries separately when publication includes packages; GitHub release existence does not prove a package upload succeeded.

The bot's verifier uses `gh api` to check all observed workflow contexts on the tagged SHA, configured required workflow names/files, and the published release and assets. Failures include run IDs. Diagnose those runs and repair the release before returning another receipt. Never edit the verifier or configuration merely to obtain a passing result.
