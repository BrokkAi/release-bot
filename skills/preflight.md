# Publishability preflight — no publication in this phase

Prepare a release covering the job target, but do not create/push release tags, create public releases, upload final assets, or publish registry packages. Inspect workflow triggers before pushing preparation commits: a push or dispatch that automatically publishes is also publication and is prohibited during preflight. Repository instructions do not override this phase boundary.

Read AGENTS.md, the configured release documents that exist, release scripts, manifests and CI workflows. Discover the procedure and checks yourself; do not ask the operator to write a bot configuration or list workflow filenames. Enumerate EVERY intended destination: GitHub assets, each crate/npm/PyPI/Maven package, container image, update feed, documentation deployment, signing/notarization service, or other publishing target. Include monorepo packages and the order of their dependencies. Existing job.plan and job.candidate are recovery evidence; reconcile any earlier partial publication.

The job target can include unpushed commits left in this managed checkout after an earlier release. These are unreleased work for this job, even when the remote branch still matches the previous release. Preserve and inspect them, include them in the prepared commit, and push them to the configured branch through the repository's normal process after checking push triggers. Complete any required PR/merge and exact-commit CI before returning ready; do not ask the operator to push the bot's work manually. Use a new version for commits after a completed release; never change that release's tag or artifacts. A rejected push or required approval is a specific blocker to report, not a reason to drop local commits or force-push.

When job.plan exists, start with that plan and job.failure: diagnose the specific failed gate or changed files and repair only what invalidated readiness. Reuse successful exact-commit CI and existing release infrastructure. Do not repeat a repository-wide audit, redesign the release process, or rerun completed test/build suites without a changed input or a specific failure. A clean unchanged prepared commit does not need another preparation commit. Return the corrected plan promptly once the required evidence is available; the daemon executes the checks and caches its successful build checks by plan and commit.

If release infrastructure is missing, create it as part of this preparation session. No previous releases, no release instructions, or an absent .github/workflows directory are reasons to bootstrap the release process, not to stop and ask the operator to design one. Infer the project's build system, deliverables, version conventions and intended destinations from its source, manifests and documentation. Respect explicitly private/non-publishable packages; do not invent registry accounts, change ownership or make private code public. Where no external registry is intended, a GitHub release with the project's appropriate deliverables is a valid starting point.

Create the missing build/package scripts, real tests and validation, CI and release workflows for GitHub repositories, and RELEASING.md explaining how the process works, its destinations and required credentials. Reuse existing infrastructure where present. Choose an initial version consistent with existing metadata and history. Build the real deliverables and define exact-version artifact verification. Configure only the permissions and environments each job needs, and preserve branch protections and required approvals. You may commit and push non-publishing setup changes, or use the repository's required PR/merge process, during preparation. The prepared commit must include the completed setup and any merged fixes.

New workflows must let setup commits and preflight runs validate without publishing. Keep publication behind an explicit release trigger; verify the trigger and its credential behavior rather than assuming a tag created by automation starts another workflow. The publication workflow must validate all destinations before its first upload, support recovery of partial results, and finalize the GitHub release only after the required artifacts and packages are complete. Run the new non-publishing checks, inspect their exact-SHA Actions results, and repair failures before returning ready. Do not count merely writing workflow YAML as a working release process.

Use credentials and publishing identities already authorized for this repository. If workflow creation, Actions execution, registry ownership, secrets, trusted-publisher setup or environment approvals require access you do not have, finish the useful non-publishing setup you can, then return blocked. Detail must identify the exact destination, workflow/job/environment, missing permission or credential, and the action the operator must take. Never create a tag or partially publish to test access. After access is repaired, continue with the same setup and normal preflight checks.

For a GitHub repository, inspect .github/workflows and determine which CI and publication workflows must run for the release commit/tag. Include their names or filenames in plan.github_workflows (an array of strings). Discover the actual names; do not assume ci.yml or release.yml. Do not list unrelated schedules or workflows whose event/path filters intentionally exclude this release. This list is required when the operator has not supplied one, and the daemon verifies it after publication.

Prepare necessary version/changelog/code/CI fixes and run the complete tests and builds for changed inputs. Reuse successful exact-commit evidence when inputs have not changed. Commit preparation changes. The plan must name the exact prepared commit and proposed tag. The publishing phase cannot change that commit. If needed, add or repair a repository preflight script/workflow that performs validation without publishing. Never replace actual checks with unconditional success.

For EACH destination establish three kinds of non-publishing checks:

- build: reproducible packaging/build/tests, metadata, dependency ordering and all expected artifacts for the committed inputs. The daemon caches successful build checks for an unchanged plan and clean commit, so keep expiring credentials, remote availability and other mutable prerequisites in authorization, version or separately named checks (which always run). Use the project's dry-run or validation mode where available. Where exact-commit CI already performed the complete build, a command may verify that specific successful run and its artifact evidence instead of rebuilding locally; it must fail on missing, failed or mismatched evidence.
- version: the exact proposed version is available, or an already-published immutable artifact is identical and can safely be reused during recovery. Plan how partial uploads will be detected and resumed. Never overwrite an existing release version blindly.
- authorization: the ACTUAL publishing identity has the permissions and ownership necessary to publish that destination. Check token expiry/scope, repository/environment restrictions, approvals and workload identity/OIDC trust as applicable. Credential presence, a secret NAME, a public metadata read, or success under a developer's different identity is not proof of publishing rights.

When publishing runs in GitHub Actions, authorization checks must execute in or inspect the same publishing job's credential/environment context. A local login does not validate a stored Actions secret. A passing unrelated CI run proves nothing about publish permission. A non-publishing preflight workflow can exercise the configured identity and report ownership/scope/trust checks; verify its exact commit, job/environment and successful conclusion through gh. Do not print secrets. If an environment approval or inaccessible credential prevents a meaningful check, report blocked before any publication.

Rust/crates.io example: inspect every publishable workspace package, registry selection, package.publish, metadata, dependencies and version. Run cargo publish --dry-run or cargo package to validate the package. This does NOT prove remote upload authorization. Separately verify the registry publishing identity, current crate ownership/team membership and credential's publish scope/expiry, or the exact trusted-publisher repository/workflow/environment configuration. First publication needs namespace and identity validation as well. Do not infer crate rights from GitHub contents:write or from cargo owner --list alone. If authorization cannot be established non-destructively, report blocked; never upload a test version to discover whether credentials work.

Return reproducible, non-publishing command arrays for the daemon to execute independently, including commands that verify successful remote preflight runs. The commands must exit nonzero for failed, unknown, incomplete or wrong-commit evidence. Each command runs in the checkout with RELEASE_COMMIT, RELEASE_TAG, RELEASE_TARGET, RELEASE_DESTINATION and RELEASE_PLAN_JSON available. Use scripts for multi-step checks. The evidence text must explain what was checked and why it validates the actual publisher. Include at least build, authorization and version for every destination. Never use echo/true or a dry-run as a substitute for a permissions check.

Every destination also requires a separate verify command array. That command runs AFTER publication and must check the exact version, artifacts, contents/checksums or registry metadata needed to establish complete publication. It must fail on partial or missing output. This prevents a GitHub release from masking a failed crate, container or other package upload.

Design checks for the full release lifecycle. A temporary private draft used to probe authorization is disposable; its deletion must not invalidate the completed workflow's evidence. The actual publishing job must recreate missing staging state and recheck its own credentials before uploads. Already-published versions go to read-only verification, not a check that requires them to remain private drafts. Preserve conflicts and permission failures as real errors.

Distinguish upload integrity from rebuild reproducibility. Compare uploads with the exact staged bytes within the publishing job. For later independent verification, validate downloaded archives against their own published manifest/checksums, then compare unpacked files, executable permissions and exact commit/version/platform metadata with the expected build. Gzip/compressor output may differ across environments despite identical contents; do not require compressed-byte equality across machines unless the complete compression toolchain is controlled. Different binaries or other payload files must still fail verification.

If all destinations have checkable evidence, finish with this single-line structure (using real values and actual commands):

RELEASE_RESULT {"status":"ready","plan":{"commit":"FULL_PREPARED_COMMIT","tag":"PROPOSED_TAG","destinations":[{"name":"registry/package","kind":"crates.io","version":"VERSION","environment":"actual workflow/job/environment or local identity","checks":[{"kind":"build","command":["path-to-real-check","build"],"evidence":"build/package checks performed"},{"kind":"authorization","command":["path-to-real-check","authorization"],"evidence":"actual publisher ownership and permission evidence"},{"kind":"version","command":["path-to-real-check","version"],"evidence":"version availability or identical existing artifact"}],"verify":["path-to-real-check","published"]}]},"detail":"preflight evidence"}

If any destination is unknown or not publishable, return RELEASE_RESULT with status "blocked" and actionable detail. No published artifact should be needed to test readiness.
